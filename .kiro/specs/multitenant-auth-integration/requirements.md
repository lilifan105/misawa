# 要件定義書

## はじめに

本システムを独立したサービスからマルチテナントSaaSプラットフォームの一部として統合するための認証・認可機能を実装する。マルチテナントサービスから発行されたJWTトークンを検証し、テナントのサービスアクセス権限を確認し、すべてのバックエンドAPIで権限チェックを実施する。

## 用語集

- **マルチテナントサービス**: マルチテナントSaaSアカウント管理基盤（親サービス）
- **文書管理システム**: 本システム（子サービス）
- **JWTトークン**: Cognitoから発行される認証トークン（IDトークン）
- **テナント**: SaaSを利用する企業顧客単位
- **サービスアクセス制御**: テナントがサービスにアクセスする権限の管理
- **RDS PostgreSQL**: マルチテナントサービスのデータベース
- **フロントエンド**: Next.jsで実装されたフロントエンドアプリケーション
- **バックエンドAPI**: Lambda関数で実装されたバックエンドAPI
- **アクセス拒否画面**: アクセス権限がない場合に表示するデフォルト画面

## 要件

### 要件1: JWTトークン検証

**ユーザーストーリー:** システムとして、マルチテナントサービスからのJWTトークンを検証し、ユーザーを認証してテナント情報を抽出したい。

#### 受入基準

1. WHEN ユーザーがAuthorizationヘッダーにJWTトークンを含めてメイン画面にアクセスする THEN 文書管理システムはヘッダーからトークンを抽出する
2. WHEN JWTトークンを受信する THEN 文書管理システムはCognitoの公開鍵（JWKS）を使用してトークンの署名を検証する
3. WHEN JWTトークンが検証される THEN 文書管理システムはトークンのクレームからcustom:tenant_name、name、custom:roleを抽出する
4. IF JWTトークンが存在しない THEN 文書管理システムは401 Unauthorizedエラーを返す
5. IF JWTトークンが無効または期限切れである THEN 文書管理システムは401 Unauthorizedエラーを返す

### 要件2: テナントサービスアクセス権限確認

**ユーザーストーリー:** システムとして、テナントのサービスアクセス権限を確認し、認可されたテナントのみが文書管理システムを使用できるようにしたい。

#### 受入基準

1. WHEN JWTトークンからcustom:tenant_nameが抽出される THEN 文書管理システムはRDS PostgreSQLデータベースにクエリしてサービスアクセス権限を確認する
2. WHEN データベースにクエリする THEN 文書管理システムはtenantテーブルでtenant_nameがcustom:tenant_nameと一致するレコードを検索しtenant_id（UUID）を取得する
3. WHEN tenant_idが取得される THEN 文書管理システムはtenant_service_subscriptionテーブルでアクティブなサブスクリプションを確認する
4. IF テナントが文書管理サービスへのアクティブなサブスクリプションを持つ THEN 文書管理システムはシステムへのアクセスを許可する
5. IF テナントがアクティブなサブスクリプションを持たない THEN 文書管理システムはアクセスを拒否しアクセス拒否画面を表示する
6. WHEN サブスクリプションステータスを確認する THEN 文書管理システムはサブスクリプションのstatusが'active'であり期限切れでないことを検証する

### 要件3: アクセス拒否画面の表示

**ユーザーストーリー:** アクセス権限のないユーザーとして、サービスにアクセスできない理由を明確に説明するメッセージを見たい。

#### 受入基準

1. WHEN テナントがアクセスを拒否される THEN 文書管理システムはアクセス拒否画面を表示する
2. WHEN アクセス拒否画面を表示する THEN 文書管理システムはサービスアクセス権限がないことを示すメッセージを表示する
3. WHEN アクセス拒否画面を表示する THEN 文書管理システムはテナント名とサービス名を表示する
4. WHEN アクセス拒否画面を表示する THEN 文書管理システムはシステム管理者の連絡先情報を提供する
5. THE アクセス拒否画面はアプリケーションの他の部分と同じヘッダーとスタイリングを維持する

### 要件4: バックエンドAPI認可

**ユーザーストーリー:** システムとして、すべてのバックエンドAPIで認可チェックを実施し、認証・認可されたユーザーのみが保護されたリソースにアクセスできるようにしたい。

#### 受入基準

1. WHEN 任意のバックエンドAPIエンドポイントが呼び出される THEN 文書管理システムはAuthorizationヘッダーに有効なJWTトークンを要求する
2. WHEN バックエンドAPIがJWTトークンを検証する THEN 文書管理システムはトークンからcustom:tenant_nameを抽出する
3. WHEN バックエンドAPIがリクエストを処理する THEN 文書管理システムはテナントがアクティブなサブスクリプションを持つことを検証する
4. WHEN バックエンドAPIがデータにアクセスする THEN 文書管理システムはすべてのクエリをtenant_idでフィルタリングしてデータ分離を保証する
5. IF 任意のバックエンドAPIで認可が失敗する THEN 文書管理システムは説明的なメッセージとともに403 Forbiddenエラーを返す

### 要件5: データベース接続設定

**ユーザーストーリー:** システムとして、マルチテナントサービスのRDS PostgreSQLデータベースに接続し、テナントのサブスクリプションを確認したい。

#### 受入基準

1. THE 文書管理システムはRDS接続パラメータ（ホスト、ポート、データベース名、ユーザー名、パスワード）を環境変数として保存する
2. WHEN RDSに接続する THEN 文書管理システムはSSL/TLS暗号化を使用する
3. WHEN データベースにクエリする THEN 文書管理システムはパフォーマンスを最適化するために接続プーリングを使用する
4. WHEN データベース接続が失敗する THEN 文書管理システムはエラーをログに記録し503 Service Unavailableエラーを返す
5. THE 文書管理システムは指数バックオフを使用した接続リトライロジックを実装する

### 要件6: フロントエンドJWTトークン処理

**ユーザーストーリー:** フロントエンドアプリケーションとして、マルチテナントサービスからJWTトークンを受信・保存し、APIリクエストに含めたい。

#### 受入基準

1. WHEN フロントエンドがマルチテナントサービスからJWTトークンを受信する（URLパラメータまたはヘッダー経由） THEN 文書管理システムはトークンを安全に保存する
2. WHEN フロントエンドがAPIリクエストを行う THEN 文書管理システムはAuthorizationヘッダーにJWTトークンを含める
3. WHEN JWTトークンが期限切れになる THEN フロントエンドは401エラーを検出しマルチテナントサービスのログインにリダイレクトする
4. THE フロントエンドはJWTトークンをlocalStorageに保存しない（sessionStorageまたはメモリのみを使用）
5. WHEN ユーザーがブラウザを閉じる THEN フロントエンドは保存されたすべてのトークンをクリアする

### 要件7: テナントコンテキストの伝播

**ユーザーストーリー:** システムとして、アプリケーション全体でテナントコンテキストを伝播し、すべての操作が正しいテナントにスコープされるようにしたい。

#### 受入基準

1. WHEN ユーザーが認証される THEN 文書管理システムはcustom:tenant_name、name、custom:roleを含むテナントコンテキストを作成する
2. WHEN 任意のリクエストを処理する THEN 文書管理システムはテナントコンテキストをすべてのバックエンドサービスに渡す
3. WHEN データベースにアクセスする THEN 文書管理システムはcustom:tenant_nameからtenant_id（UUID）を解決しすべてのWHERE句に自動的にtenant_idを含める
4. WHEN イベントをログに記録する THEN 文書管理システムはすべてのログエントリにtenant_nameとtenant_idを含める
5. THE 文書管理システムはデータベースクエリレベルでtenant_idフィルタリングを強制することでクロステナントデータアクセスを防止する

### 要件8: エラーハンドリングとログ記録

**ユーザーストーリー:** システム管理者として、認証・認可の失敗に関する包括的なエラーログを取得し、問題をトラブルシューティングしたい。

#### 受入基準

1. WHEN JWT検証が失敗する THEN 文書管理システムは失敗理由（無効な署名、期限切れトークン、クレーム欠落）をログに記録する
2. WHEN データベース接続が失敗する THEN 文書管理システムは接続詳細（認証情報を除く）とともにエラーをログに記録する
3. WHEN サブスクリプション検証が失敗する THEN 文書管理システムはtenant_name、tenant_id、service_idをログに記録する
4. WHEN 認可が拒否される THEN 文書管理システムはtenant_name、tenant_id、ユーザー、リクエストされたリソースをログに記録する
5. THE 文書管理システムは一貫したフィールド（タイムスタンプ、レベル、tenant_name、tenant_id、ユーザー、アクション、結果）を持つ構造化ログを使用する

### 要件9: マルチテナントデータベースへのサービス登録

**ユーザーストーリー:** システム管理者として、文書管理システムをマルチテナントサービスデータベースに登録し、テナントがサブスクライブできるようにしたい。

#### 受入基準

1. THE 文書管理システムは一意のservice_idでserviceテーブルに登録される
2. THE serviceレコードはservice_name、description、service_url、icon_urlを含む
3. THE service_urlは文書管理システムのフロントエンドURLを指す
4. THE serviceレコードはstatusが'active'に設定される
5. THE service_idはアクセスを許可するためにtenant_service_subscriptionレコードで使用される

### 要件10: 既存認証との統合

**ユーザーストーリー:** システムとして、既存のCognito認証と統合しながら後方互換性を維持し、スタンドアロンモードとマルチテナントモードの両方で動作できるようにしたい。

#### 受入基準

1. THE 文書管理システムはスタンドアロンモード（既存のCognito）とマルチテナントモード（親サービスからのJWT）の両方をサポートする
2. WHEN マルチテナントモードの場合 THEN 文書管理システムはスタンドアロンログインページをスキップする
3. WHEN スタンドアロンモードの場合 THEN 文書管理システムは既存の認証フローを使用する
4. THE モードは環境変数（MULTITENANT_MODE=true/false）によって決定される
5. WHEN モードを切り替える THEN 文書管理システムはコード変更を必要とせず、設定更新のみで対応する
