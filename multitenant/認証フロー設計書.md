## 1. 概要

本システムでは、Amazon Cognitoという認証サービスを使用し、2つの認証方式をサポートします。

### 1.1 サポートする認証方式

| 認証方式 | 説明 | 利用シーン |
|---------|------|----------|
| **Cognito ID/PW認証** | システム独自のID・パスワードでログイン | 既存の社内システムがない企業 |
| **SSO認証** | 既存の社内システム（EntraID等）でログイン | 既に社内システムを持つ企業 |

### 1.2 どちらの認証方式でも同じ

- ログイン後の画面は同じ
- 使える機能は同じ
- 違いは「ログイン画面の見た目」だけ

---

## 2. 認証方式の種類

### 2.1 テナントごとに認証方式を設定

各企業（テナント）は、自社に合った認証方式を選択できます。

**例:**

| 企業名 | テナントID | 認証方式 |
|-------|-----------|---------|
| A株式会社 | tenant-001 | Cognito ID/PW |
| B株式会社 | tenant-002 | SSO（EntraID） |
| C株式会社 | tenant-003 | SSO（EntraID） |

### 2.2 ログイン時の流れ

```
ユーザーがテナントIDを入力
  ↓
システムがテナント情報を確認
  ↓
認証方式に応じたログイン画面を表示
```

## 3. Cognito ID/PW認証フロー

### 3.1 概要

システム独自のID・パスワードでログインする方式です。

### 3.2 ログインの流れ

![Cognito ID/PW認証フロー](./material/cognito-auth-flow.png)

**詳細:**

```
【ステップ1】ログイン画面
ユーザー: テナントID、ユーザー名を入力
  ↓
【ステップ2】認証方式の確認
システム: テナント情報を確認
システム: 「Cognito ID/PW認証」と判定
  ↓
【ステップ3】パスワード入力画面へ移動
システム: Cognitoのログイン画面を表示
  ↓
【ステップ4】パスワード入力
ユーザー: パスワードを入力
  ↓
【ステップ5】認証
Cognito: ユーザー名・パスワードを確認
Cognito: ✅ 認証成功
  ↓
【ステップ6】ログイン完了
システム: 認証チケット（JWT）を発行
システム: ポータル画面を表示
```

### 3.3 ユーザー情報の管理

ユーザー情報はCognitoに保存されます：

| 項目 | 例 | 説明 |
|------|---|------|
| ユーザー名 | tenant-001#user01 | テナントID + ユーザー名 |
| メールアドレス | user@example.com | 連絡先 |
| テナントID | tenant-001 | 所属企業 |
| ロール | user | 権限（一般ユーザー、管理者など） |

**ポイント:**
- ユーザー名は「テナントID#ユーザー名」の形式
- 異なる企業で同じユーザー名（例: admin）を使用可能

## 4. SSO認証フロー

### 4.1 概要

既存の社内システム（EntraID等）のID・パスワードでログインする方式です。

**メリット:**
- 社員は普段使っているID・パスワードでログイン可能
- パスワードを複数覚える必要がない
- 退職時に社内システムのアカウントを削除すれば、自動的にこのシステムにもログインできなくなる

### 4.2 ログインの流れ

![SSO認証フロー](./material/sso-auth-flow.png)

**詳細:**

```
【ステップ1】ログイン画面
ユーザー: テナントID、ユーザー名を入力
  ↓
【ステップ2】認証方式の確認
システム: テナント情報を確認
システム: 「SSO認証（EntraID）」と判定
  ↓
【ステップ3】社内システムのログイン画面へ移動
システム: EntraIDのログイン画面へ自動転送
  ↓
【ステップ4】社内システムでログイン
ユーザー: 普段使っているID・パスワードを入力
EntraID: 認証を実行
EntraID: ✅ 認証成功
  ↓
【ステップ5】認証結果をCognitoへ送信
EntraID: 「このユーザーは本物です」という証明書を発行
EntraID: 証明書をCognitoへ送信
  ↓
【ステップ6】Cognitoが証明書を確認
Cognito: EntraIDの証明書を検証
Cognito: ✅ 本物の証明書と確認
  ↓
【ステップ7】ログイン完了
Cognito: 認証チケット（JWT）を発行
システム: ポータル画面を表示
```

### 4.3 重要なポイント

#### 4.3.1 ポータル画面は認証方式を意識しない

ステップ7以降は、Cognito ID/PW認証と完全に同じです：

- 同じ認証チケット（JWT）を受け取る
- 同じポータル画面が表示される
- 使える機能も同じ

**つまり:**
- ユーザーから見ると、ログイン画面が違うだけ
- システムから見ると、どちらも「Cognitoが認証したユーザー」として扱う

#### 4.3.2 ユーザー情報の管理

SSO認証でも、Cognitoにユーザー情報が保存されます：

| 情報の保存場所 | 役割 |
|-------------|------|
| EntraID（社内システム） | マスター情報（本物のユーザー情報） |
| Cognito | コピー情報（このシステム用） |

**初回ログイン時:**
1. EntraIDで認証成功
2. EntraIDからユーザー情報を取得
3. Cognitoにユーザー情報をコピー
4. 以降、Cognitoの情報を使用

## 5. 信頼関係の仕組み

### 5.1 なぜCognitoはEntraIDを信頼できるのか？

SSO認証では、「EntraIDが認証したユーザー」をCognitoが信頼する必要があります。

**疑問:**
- 悪意のある人が「私はEntraIDです」と偽って証明書を送ったら？
- どうやって本物のEntraIDからの証明書だと確認するのか？

**答え: デジタル署名**

### 5.2 デジタル署名の仕組み（印鑑証明の例え）

デジタル署名は、銀行の印鑑証明のようなものです。

#### 5.2.1 印鑑証明の例

```
【銀行での手続き】

1. あなたが書類に印鑑を押す
   ↓
2. 銀行員が印鑑を確認
   ↓
3. 銀行に登録されている印鑑と照合
   ↓
4. ✅ 一致 → 本人確認OK
   ❌ 不一致 → 偽物
```

**ポイント:**
- 印鑑は偽造が難しい
- 銀行に登録された印鑑と照合できる
- 本人しか持っていない

#### 5.2.2 デジタル署名の例

```
【SSO認証での確認】

1. EntraIDが証明書に「デジタル印鑑」を押す
   ↓
2. Cognitoが「デジタル印鑑」を確認
   ↓
3. 事前に登録されたEntraIDの「印鑑」と照合
   ↓
4. ✅ 一致 → EntraIDからの本物の証明書
   ❌ 不一致 → 偽物
```

**ポイント:**
- デジタル印鑑（秘密鍵）はEntraIDだけが持っている
- 偽造は事実上不可能
- Cognitoは事前に登録された「印鑑の見本」（公開鍵）で確認できる

### 5.3 事前設定（信頼関係の構築）

SSO認証を使うには、事前にCognitoとEntraIDを相互に登録する必要があります。

#### 5.3.1 EntraID側の設定

```
EntraIDの管理画面で設定:
- このシステム（Cognito）を「信頼するアプリケーション」として登録
- Cognitoの情報（識別子、応答URL）を登録
- デジタル署名用の証明書を自動生成
```

#### 5.3.2 Cognito側の設定

```
Cognitoの管理画面で設定:
- EntraIDを「信頼するIdP」として登録
- EntraIDの情報（エンドポイント、証明書）を登録
- ユーザー情報のマッピング設定
```

### 5.4 信頼関係の確認フロー

![信頼関係の確認フロー](./material/trust-relationship-flow.png)

**詳細:**

```
【ステップ1】Cognitoが認証リクエストを送信
Cognito → EntraID: 「このユーザーを認証してください」
（Cognitoのデジタル署名付き）
  ↓
【ステップ2】EntraIDが署名を確認
EntraID: Cognitoの署名を検証
EntraID: ✅ 本物のCognitoからのリクエスト
  ↓
【ステップ3】ユーザー認証
EntraID: ユーザーにログイン画面を表示
ユーザー: ID・パスワードを入力
EntraID: ✅ 認証成功
  ↓
【ステップ4】EntraIDが証明書を返す
EntraID → Cognito: 「このユーザーは本物です」
（EntraIDのデジタル署名付き）
  ↓
【ステップ5】Cognitoが署名を確認
Cognito: EntraIDの署名を検証
Cognito: ✅ 本物のEntraIDからの証明書
Cognito: ユーザーを信頼してログイン許可
```

**まとめ:**
- お互いにデジタル署名で本人確認
- 偽造は事実上不可能
- 安全にSSO認証が実現できる

## 6. JWTトークンとは

### 6.1 概要

JWT（ジェイダブリューティー）は、「認証チケット」のようなものです。

**例え:**
- 遊園地の入場チケット
- 映画館のチケット
- 電車の切符

### 6.2 JWTの役割

![JWTトークンの使用フロー](./material/jwt-usage-flow.png)

**詳細:**

```
【ログイン時】
ユーザー: ID・パスワードを入力
Cognito: ✅ 認証成功
Cognito: JWTチケットを発行
  ↓
【ポータル画面アクセス時】
ユーザー: JWTチケットを提示
システム: チケットを確認
システム: ✅ 有効なチケット → 画面を表示
  ↓
【APIアクセス時】
ユーザー: JWTチケットを提示
API: チケットを確認
API: ✅ 有効なチケット → データを返す
```

### 6.3 JWTに含まれる情報

JWTには、ユーザー情報が含まれています：

| 情報 | 例 | 説明 |
|------|---|------|
| ユーザーID | a1b2c3d4-... | システム内の一意な識別子 |
| ユーザー名 | tenant-001#user01 | ログイン名 |
| メールアドレス | user@example.com | 連絡先 |
| テナントID | tenant-001 | 所属企業 |
| ロール | user | 権限（一般ユーザー、管理者など） |
| 有効期限 | 2025-12-03 18:00 | チケットの有効期限 |

### 6.4 JWTの種類

Cognitoは3種類のチケットを発行します：

| チケットの種類 | 用途 | 有効期限 |
|-------------|------|---------|
| IDトークン | ユーザー情報の確認 | 60分 |
| アクセストークン | API呼び出し | 60分 |
| リフレッシュトークン | チケットの更新 | 30日 |

**使い分け:**
- **IDトークン**: 「このユーザーは誰か」を確認
- **アクセストークン**: 「このユーザーはAPIを使っていいか」を確認
- **リフレッシュトークン**: 有効期限が切れたら新しいチケットを発行

### 6.5 JWTの安全性

#### 6.5.1 偽造防止

JWTにもデジタル署名が付いています：

```
JWT = ユーザー情報 + Cognitoのデジタル署名
```

**確認方法:**
1. システムがJWTを受け取る
2. Cognitoの署名を検証
3. ✅ 本物 → ユーザー情報を信頼
4. ❌ 偽物 → アクセス拒否

#### 6.5.2 有効期限

JWTには有効期限があります：

```
【60分後】
システム: JWTの有効期限を確認
システム: ❌ 期限切れ
システム: 再ログインを要求
```

**または:**

```
【60分後】
ユーザー: リフレッシュトークンを提示
Cognito: 新しいJWTを発行
ユーザー: ログインし直さずに継続利用
```

### 6.6 Cognito ID/PW認証とSSO認証のJWT

**重要:** どちらの認証方式でも、JWTの形式は同じです。

| 項目 | Cognito ID/PW | SSO認証 |
|------|--------------|---------|
| JWTの形式 | 同じ | 同じ |
| 含まれる情報 | 同じ | 同じ |
| 有効期限 | 同じ | 同じ |
| 使い方 | 同じ | 同じ |

**唯一の違い:**
- SSO認証の場合、JWTに「どのIdPで認証したか」の情報が追加される（オプション）

**ポータル画面から見ると:**
- どちらの認証方式でも同じJWTを受け取る
- 認証方式を意識する必要がない
- 同じ処理で動作する

## 付録

### 用語集

| 用語 | 説明 |
|------|------|
| JWT | 認証チケット。ユーザー情報と有効期限が含まれる |
| SSO | シングルサインオン。一度のログインで複数のシステムを利用できる |
| IdP | Identity Provider。認証情報を提供するサービス（EntraID等） |
| Cognito | AWSの認証サービス。本システムの認証基盤 |
| EntraID | Microsoftの認証サービス（旧Azure AD） |
| デジタル署名 | 電子的な印鑑。偽造防止のために使用 |
| 秘密鍵 | デジタル署名を作成するための鍵。本人だけが持つ |
| 公開鍵 | デジタル署名を検証するための鍵。誰でも見られる |
| SAML | SSO認証の標準プロトコル |
