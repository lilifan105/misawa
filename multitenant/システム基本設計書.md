## 1. システム概要

### 1.1 目的

SaaSビジネスにおいて複数の企業顧客（テナント）に対して効率的かつセキュアにサービスを提供できる基盤を構築する。特にテナントごとの認証要件（ID/PWまたは既存IdPとのSSO）に対応しつつ、運用負荷を軽減する仕組みを実現する。

### 1.2 目標

- **アカウント管理の一元化**: Amazon Cognitoをユーザーディレクトリとして利用し、全テナントのユーザーを一元管理する
- **柔軟な認証方法の提供**: テナント固有の認証要件（ID/PW認証、EntraID等とのSSO）に対応する
- **セキュアなアクセス制御**: ユーザーのテナント帰属情報に基づき、契約済みサービスへのアクセスを適切に制御する
- **スケーラビリティと運用効率**: 将来のテナント数増加に対応可能なアーキテクチャとする

### 1.3 主要機能

| 機能分類 | 機能名 | 概要 |
|---------|--------|------|
| 認証・認可 | ユーザー認証機能 | ID/PW認証、外部IdP（SAML/OIDC対応）によるSSO |
| 認証・認可 | アクセス制御機能 | テナント帰属とロールに基づくアクセス制御 |
| テナント管理 | テナント登録管理 | 新規テナントの登録と初期設定 |
| テナント管理 | 外部IdP設定管理 | SAML/OIDC連携設定の管理 |
| ユーザー管理 | ユーザー登録管理 | テナント内のユーザー登録、更新、削除 |
| ユーザー管理 | ロール管理 | ユーザーのロール（権限）設定 |
| サービス管理 | サービス登録管理 | SaaSで提供するサービスの管理 |
| サービス管理 | 契約管理 | テナント・サービス間の契約関係管理 |
| ポータル | 契約サービス表示 | 認証済みユーザーの契約サービス一覧表示 |
| ポータル | サービスアクセス | 契約サービスへのシングルサインオン |

## 2. システム構成

### 2.1 システム構成図

![システム構成図](./material/architecture.png)

**主要コンポーネント:**
- **CloudFront**: CDN、SSL/TLS終端、静的コンテンツ配信
- **S3**: Next.js Static Exportによる静的ウェブホスティング
- **Cognito User Pool**: 認証基盤（ID/PW、SAML/OIDC SSO対応）
- **API Gateway**: APIエンドポイント、Cognito Authorizerによる認証
- **Lambda**: ビジネスロジック実行（Python/FastAPI）
- **RDS PostgreSQL**: データストア（tenant、service、subscription）

### 2.2 ネットワーク構成

#### 2.2.1 パブリックアクセス層
- **CloudFront**: インターネットからの唯一のエントリーポイント
  - HTTPS通信のみ許可
  - WAF統合（オプション）
  - カスタムドメイン対応

#### 2.2.2 アプリケーション層
- **S3**: CloudFrontからのアクセスのみ許可（OAI使用）
- **API Gateway**: Cognito Authorizerによる認証必須
- **Lambda**: VPC内配置（オプション、DynamoDB VPCエンドポイント使用時）

#### 2.2.3 データ層
- **RDS PostgreSQL**: VPC内に配置、Lambdaからのみアクセス
- **Cognito User Pool**: AWS管理サービス

- 高速なページロード

### 3.2 レイヤー構成

![レイヤー構成図](./material/layer-architecture.png)

**各レイヤーの責務:**

| レイヤー | 技術 | 責務 |
|---------|------|------|
| プレゼンテーション層 | Next.js + CloudFront + S3 | UI表示、ユーザー操作、静的コンテンツ配信 |
| 認証・認可層 | Cognito + API Gateway Authorizer | JWT発行・検証、テナント識別、RBAC |

| データ永続化層 | RDS PostgreSQL | データ永続化、トランザクション管理、リレーショナルデータ管理 |

### 3.3 マルチテナント設計

#### 3.3.1 テナント識別方式

**Cognitoカスタム属性によるテナント識別**
- ユーザー作成時に`tenant_id`をカスタム属性として設定
- Cognitoのusernameは `{tenant_id}#{username}` 形式で保存（例: `tenant-001#user01`）
- JWT内のカスタムクレームとして`tenant_id`を含める
- すべてのAPIリクエストでJWTから`tenant_id`を抽出

```json
{
  "sub": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "email": "user@example.com",
  "custom:tenant_id": "tenant-001",
  "custom:role": "user",
  "cognito:username": "tenant-001#user01"
}
```

**ユーザー名の命名規則:**
- テナント内でユーザー名が一意であればよい（グローバルに一意である必要はない）
- 異なるテナントで同じユーザー名（例: `admin`）を使用可能
- Cognitoレベルでは `{tenant_id}#{username}` で一意性を保証

#### 3.3.2 データ分離方式

**論理的分離（WHERE句によるフィルタリング）**
- すべてのクエリで`tenant_id`をWHERE条件として使用
- Row Level Security（RLS）による自動的なテナント分離（オプション）
- テナント間のデータ漏洩を防止

**例: tenant_service_subscriptionテーブルのクエリ**
```sql
SELECT * FROM tenant_service_subscription 
WHERE tenant_id = 'tenant-001';
```

#### 3.3.3 テナント別認証方式

| 認証方式 | 設定値 | 説明 |
|---------|--------|------|
| ID/PW認証 | COGNITO_PW | Cognito標準のユーザー名・パスワード認証 |
| SAML SSO | SAML | 外部IdP（EntraID等）とのSAML連携 |
| OIDC SSO | OIDC | 外部IdP（Auth0等）とのOIDC連携 |

## 4. コンポーネント設計

### 4.1 フロントエンドコンポーネント

#### 4.1.1 技術スタック
- **フレームワーク**: Next.js 14+ (App Router)
- **言語**: TypeScript
- **UIライブラリ**: AWS Amplify UI Components
- **状態管理**: React Context API / Zustand
- **HTTPクライアント**: fetch API / axios

#### 4.1.2 主要コンポーネント

**ページコンポーネント**
- ログイン画面（テナントID、ユーザー名入力）
- ポータル画面（契約サービス一覧表示）
- 認証コールバック処理ページ
- 管理画面（システム管理者、テナント管理者向け）

**共通コンポーネント**
- ヘッダー（ユーザー情報、ログアウトボタン）
- サービスカード（契約サービスの表示）
- 認証ガード（未認証ユーザーのアクセス制御）

**ユーティリティ**
- API呼び出しラッパー
- 認証処理（JWT管理）
- Cognito設定

#### 4.1.3 認証フロー

認証フローの詳細については、別ドキュメント「[認証フロー詳細設計書](./06_認証フロー詳細設計書.md)」を参照してください。

**概要:**
- テナントIDを指定してログイン
- テナントごとに認証方式を選択可能（Cognito ID/PW または SSO）
- 認証後、JWTトークンを発行してポータル画面へ遷移

### 4.2 バックエンドコンポーネント

#### 4.2.1 技術スタック
- **言語**: Python 3.11+
- **フレームワーク**: FastAPI
- **実行環境**: AWS Lambda
- **ORMライブラリ**: Pydantic（データバリデーション）
- **AWSクライアント**: boto3

#### 4.2.2 Lambda関数構成

**主要API**
- テナント管理API（テナントの登録、更新、削除）
- サービス管理API（サービスの登録、更新、削除）
- 契約管理API（テナントとサービスの契約関係管理）
- ユーザー管理API（ユーザーの登録、更新、削除）

#### 4.2.3 共通モジュール

**JWT検証モジュール**
- CognitoのJWTトークンを検証
- JWKSを使用して署名を検証
- ユーザー情報（クレーム）を取得

**データベース接続モジュール**
- RDS PostgreSQLへの接続管理
- コネクションプーリング
- SQLクエリの実行
- トランザクション管理

#### 4.2.4 データモデル

**Tenantモデル**
- テナントID（UUID）
- テナント企業名
- ステータス（active、suspended等）
- 契約開始日
- 認証方式（COGNITO_PW、SAML、OIDC）
- IdP名（オプション）

**Serviceモデル**
- サービスID（UUID）
- サービス名
- 説明
- サービスURL
- アイコンURL（オプション）

**Subscriptionモデル**
- サブスクリプションID
- テナントID
- サービスID
- アクセスレベル（BASIC、PREMIUM、ENTERPRISE）

### 4.3 認証・認可コンポーネント

#### 4.3.1 Amazon Cognito設定

**User Pool設定**
- パスワードポリシー
  - 最小8文字
  - 大文字、小文字、数字、記号を必須
- カスタム属性
  - tenant_id（変更不可、必須）
  - role（変更可能、オプション）
- 高度なセキュリティモード有効化

**Hosted UI設定**
- OAuth設定
  - フロー: Authorization Code
  - スコープ: openid、email、profile
- コールバックURL設定
- トークン有効期限
  - アクセストークン: 60分
  - IDトークン: 60分
  - リフレッシュトークン: 30日

#### 4.3.2 API Gateway Authorizer

**Cognito Authorizer設定**
- タイプ: Cognito User Pools
- 認証ソース: Authorizationヘッダー
- JWTクレームの自動検証
- 全APIエンドポイントで認証必須

#### 4.3.3 ロールベースアクセス制御（RBAC）

**権限チェックロジック**

| ロール | アクセス範囲 |
|--------|------------|
| システム管理者 | 全テナント、全機能にアクセス可能 |
| テナント管理者 | 自テナントのみアクセス可能（ユーザー管理、設定変更） |
| 一般ユーザー | 自テナントの契約サービスのみアクセス可能 |

**認可チェックの流れ:**
1. JWTからユーザーのロールとテナントIDを取得
2. リクエストされたリソースのテナントIDと照合
3. ロールに応じたアクセス権限を判定
4. 権限がある場合のみ処理を実行

### 4.4 データストアコンポーネント

#### 4.4.1 RDS PostgreSQLテーブル設計

データベース設計の詳細については、別ドキュメント「[データベース設計書](./02_データベース設計書.md)」を参照してください。

**主要テーブル:**

**tenantテーブル**
- tenant_id (UUID, Primary Key)
- tenant_name (VARCHAR)
- status (VARCHAR): active | suspended | trial | expired
- contract_start_date (DATE)
- auth_method (VARCHAR): COGNITO_PW | SAML | OIDC
- identity_provider_name (VARCHAR, NULL可)
- created_at (TIMESTAMP)
- updated_at (TIMESTAMP)

**serviceテーブル**
- service_id (UUID, Primary Key)
- service_name (VARCHAR)
- description (TEXT, NULL可)
- service_url (VARCHAR)
- icon_url (VARCHAR, NULL可)
- created_at (TIMESTAMP)

**tenant_service_subscriptionテーブル**
- subscription_id (UUID, Primary Key)
- tenant_id (UUID, Foreign Key → tenant)
- service_id (UUID, Foreign Key → service)
- access_level (VARCHAR): BASIC | PREMIUM | ENTERPRISE
- subscribed_at (TIMESTAMP)
- INDEX: (tenant_id, service_id)
- INDEX: (service_id)

## 5. データフロー

認証フローの詳細については、別ドキュメント「[認証フロー詳細設計書](./06_認証フロー詳細設計書.md)」を参照してください。

**認証フローの概要:**

![認証フロー図](../diagrams/auth-flow.png)

**認証フローの特徴:**
- テナントIDの明示的な指定によるテナント識別
- テナントの認証方式（COGNITO_PW / SAML / OIDC）に応じた動的な認証フロー切り替え
- Cognitoユーザー名は `{tenant_id}#{username}` 形式で管理（テナント内でユーザー名が一意）
- JWT内のカスタムクレーム（tenant_id、role）による認可制御

### 5.2 テナント管理フロー

![テナント管理フロー](./material/tenant-management-flow.png)

**主要処理:**
1. **新規テナント登録**: システム管理者による新規テナント作成、初期管理者ユーザー作成
2. **外部IdP設定**: SAML/OIDC連携設定、Cognito Identity Provider作成

### 5.3 サービスアクセスフロー

![サービスアクセスフロー](./material/service-access-flow.png)

- JWT内のtenant_idによるテナント識別
- RDS PostgreSQLのtenant_service_subscriptionテーブルによる契約確認
- 契約がある場合のみサービスへのアクセスを許可

## 6. 非機能要件

### 6.1 パフォーマンス要件

| 項目 | 目標値 | 測定方法 |

| 項目 | 初期値 | 拡張目標 | 実現方法 |

### 6.4 セキュリティ要件

| 項目 | 要件 | 実現方法 |
|------|------|---------|

| セッション管理 | JWT有効期限60分 | Cognito Token Validity |

### 6.5 運用要件

| 項目 | 要件 | 実現方法 |

### A. 用語集

| 用語 | 説明 |
|------|------|
| テナント | SaaSを利用する企業顧客単位 |
| マルチテナント | 単一のインフラで複数の企業顧客をサポートする方式 |
| SSO | Single Sign-On、一度の認証で複数サービスにアクセス可能 |
| SAML | Security Assertion Markup Language、SSO標準プロトコル |
| OIDC | OpenID Connect、OAuth 2.0ベースの認証プロトコル |
| JWT | JSON Web Token、認証情報を含むトークン |
