## 1. データベース概要

### 1.1 データベース選定

**採用技術**: Amazon RDS PostgreSQL

**選定理由**:
- **明確なリレーションシップ**: テナント、サービス、契約の関係がRDBに適している
- **トランザクション保証**: データ整合性が重要な操作に対応
- **複雑なクエリ**: JOINを使った柔軟な検索が可能
- **PoC環境に適したコスト**: 小規模スタートに適した価格設定
- **運用の容易さ**: 自動バックアップ、パッチ適用が自動化

**DynamoDBからの変更理由**:
- データモデルが典型的なリレーショナル構造
- トランザクション要件が明確
- 初期規模（10社）ならRDBで十分
- JOINを使った検索が頻繁に発生

### 1.2 データベース構成（PoC環境）

| 項目 | 設定値 | 説明 |
|------|--------|------|
| エンジン | PostgreSQL | 15.x |
| リージョン | ap-northeast-1 | 東京リージョン |
| インスタンスクラス | db.t3.micro | PoC用（2vCPU、1GB RAM） |
| ストレージ | 20GB（汎用SSD） | 初期容量 |
| マルチAZ | 無効 | PoC環境のためシングルAZ |
| 暗号化 | 有効 | EBS暗号化 |
| 自動バックアップ | 有効（保持期間7日） | 日次バックアップ |
| パブリックアクセス | 無効 | VPC内からのみアクセス |

## 2. テナント分離設計

### 2.1 分離方式

**採用方式**: Pool Model（論理的分離）

マルチテナントアーキテクチャにおいて、単一のデータベースで複数テナントのデータを管理し、
WHERE句によるフィルタリングで論理的な分離を実現する。

**Pool Modelの特徴**:
- ✅ リソースの効率的な共有
- ✅ 運用コストの削減
- ✅ スケーラビリティの向上
- ⚠️ テナント間のデータ漏洩防止が重要

### 2.2 テナント識別方式

**WHERE句による分離**

すべてのテーブルで`tenant_id`カラムを含め、
クエリ時に必ず`WHERE tenant_id = ?`でフィルタリングすることでテナント間のデータ分離を保証する。

**例: 契約サービス取得**
```sql
SELECT s.service_name, tss.access_level
FROM tenant_service_subscription tss
JOIN service s ON tss.service_id = s.service_id
WHERE tss.tenant_id = 'tenant-001'
  AND tss.status = 'active';
```

### 2.3 データ分離の保証

**アプリケーションレベルでの制御**

1. **JWT検証**: すべてのAPIリクエストでJWTから`tenant_id`を抽出
2. **強制フィルタリング**: SQLクエリに必ず`WHERE tenant_id = ?`条件を含める
3. **権限チェック**: ユーザーのテナント帰属とリクエストのテナントIDが一致することを確認

**Row Level Security（RLS）の活用（オプション）**

PostgreSQLのRLS機能を使用して、データベースレベルでテナント分離を強制することも可能。

```sql
-- RLSポリシーの例
ALTER TABLE tenant_service_subscription ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_policy ON tenant_service_subscription
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
```

### 2.4 テナント分離のメリット・デメリット

| 項目 | Pool Model | Silo Model（参考） |
|------|-----------|-------------------|
| リソース効率 | ◎ 高い | △ 低い（テナントごとにDB） |
| 運用コスト | ◎ 低い | △ 高い |
| データ分離 | △ 論理的分離 | ◎ 物理的分離 |
| スケーラビリティ | ◎ 高い | △ 中程度 |
| 初期コスト | ◎ 低い | △ 高い |
| 適用ケース | 本プロジェクト | 高セキュリティ要件 |

## 3. テーブル設計

### 3.1 tenantテーブル（企業情報）

**概要**: テナント企業のマスタ情報を管理

**テーブル定義**:

```sql
CREATE TABLE tenant (
    tenant_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_name VARCHAR(255) NOT NULL,
    status VARCHAR(50) NOT NULL DEFAULT 'active',
    contract_start_date DATE NOT NULL,
    auth_method VARCHAR(50) NOT NULL DEFAULT 'COGNITO_PW',
    identity_provider_name VARCHAR(255),
    identity_provider_metadata JSONB,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    CONSTRAINT chk_status CHECK (status IN ('active', 'suspended', 'trial', 'expired')),
    CONSTRAINT chk_auth_method CHECK (auth_method IN ('COGNITO_PW', 'SAML', 'OIDC'))
);

-- 更新日時の自動更新トリガー
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = CURRENT_TIMESTAMP;
    RETURN NEW;
END;
$$ language 'plpgsql';

CREATE TRIGGER update_tenant_updated_at BEFORE UPDATE ON tenant
    FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
```

**カラム説明**:

| カラム名 | データ型 | 制約 | 説明 |
|---------|---------|------|------|
| tenant_id | UUID | PK | テナントID（自動生成） |
| tenant_name | VARCHAR(255) | NOT NULL | テナント企業名 |
| status | VARCHAR(50) | NOT NULL | ステータス |
| contract_start_date | DATE | NOT NULL | 契約開始日 |
| auth_method | VARCHAR(50) | NOT NULL | 認証方式 |
| identity_provider_name | VARCHAR(255) | NULL | 外部IdP名 |
| identity_provider_metadata | JSONB | NULL | IdP設定情報 |
| created_at | TIMESTAMP | NOT NULL | 作成日時 |
| updated_at | TIMESTAMP | NOT NULL | 更新日時 |

**ステータス定義**:

| ステータス | 説明 | ログイン可否 |
|-----------|------|-------------|
| active | 通常利用可能 | ✓ |
| suspended | 一時停止 | ✗ |
| trial | トライアル期間中 | ✓ |
| expired | 契約期限切れ | ✗ |

**認証方式定義**:

| 認証方式 | 説明 | 必要な追加設定 |
|---------|------|---------------|
| COGNITO_PW | ID/パスワード認証 | なし |
| SAML | SAML 2.0 SSO | identity_provider_metadata |
| OIDC | OpenID Connect SSO | identity_provider_metadata |

**データ例**:
```sql
INSERT INTO tenant (tenant_name, company_name, status, contract_start_date, auth_method, identity_provider_name)
VALUES ('sample-company', '株式会社サンプル', 'active', '2025-01-01', 'SAML', 'EntraID-Sample');
```

**運用上の注意**:
- `tenant_name`はユーザーがログイン時に入力するテナントIDとして使用（例: `sample-company`）
- `company_name`は管理画面やUIで企業名を表示する際に使用（例: `株式会社サンプル`）
- `tenant_id`（UUID）は内部的なデータベースの主キーとして使用

### 3.3 tenant_service_subscriptionテーブル（契約情報）

**概要**: テナントとサービスの契約関係を管理

**テーブル定義**:

```sql
CREATE TABLE tenant_service_subscription (
    subscription_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL,
    service_id UUID NOT NULL,
    access_level VARCHAR(50) NOT NULL DEFAULT 'BASIC',
    subscribed_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP,
    status VARCHAR(50) NOT NULL DEFAULT 'active',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    CONSTRAINT fk_tenant FOREIGN KEY (tenant_id) REFERENCES tenant(tenant_id) ON DELETE CASCADE,
    CONSTRAINT fk_service FOREIGN KEY (service_id) REFERENCES service(service_id) ON DELETE CASCADE,
    CONSTRAINT chk_access_level CHECK (access_level IN ('BASIC', 'PREMIUM', 'ENTERPRISE')),
    CONSTRAINT chk_subscription_status CHECK (status IN ('active', 'suspended', 'expired')),
    CONSTRAINT uq_tenant_service UNIQUE (tenant_id, service_id)
);

CREATE TRIGGER update_subscription_updated_at BEFORE UPDATE ON tenant_service_subscription
    FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
```

**カラム説明**:

| カラム名 | データ型 | 制約 | 説明 |
|---------|---------|------|------|
| subscription_id | UUID | PK | サブスクリプションID |
| tenant_id | UUID | FK, NOT NULL | テナントID |
| service_id | UUID | FK, NOT NULL | サービスID |
| access_level | VARCHAR(50) | NOT NULL | アクセスレベル |
| subscribed_at | TIMESTAMP | NOT NULL | 契約日時 |
| expires_at | TIMESTAMP | NULL | 契約終了日時 |
| status | VARCHAR(50) | NOT NULL | ステータス |
| created_at | TIMESTAMP | NOT NULL | 作成日時 |
| updated_at | TIMESTAMP | NOT NULL | 更新日時 |

**アクセスレベル定義**:

| レベル | 説明 | 想定用途 |
|--------|------|---------|
| BASIC | 基本機能のみ | 小規模企業向け |
| PREMIUM | 高度な機能を含む | 中規模企業向け |
| ENTERPRISE | すべての機能 | 大規模企業向け |

**データ例**:
```sql
INSERT INTO tenant_service_subscription (tenant_id, service_id, access_level, expires_at)
VALUES (
    'tenant-uuid-here',
    'service-uuid-here',
    'PREMIUM',
    '2026-01-01 00:00:00'
);
```

## 6. データ整合性

### 6.1 整合性制約

PostgreSQLの制約機能を活用してデータ整合性を保証する。

**実装済みの制約**:

1. **主キー制約（PRIMARY KEY）**
   - すべてのテーブルでUUID型の主キーを使用
   - 一意性を保証

2. **外部キー制約（FOREIGN KEY）**
   - tenant_service_subscription → tenant
   - tenant_service_subscription → service
   - 参照整合性を保証
   - CASCADE削除により関連データも自動削除

3. **一意性制約（UNIQUE）**
   - tenant_service_subscription: (tenant_id, service_id)
   - 同じテナントが同じサービスを重複契約できない

4. **CHECK制約**
   - status、auth_method、access_levelの値を制限
   - 不正な値の登録を防止

5. **NOT NULL制約**
   - 必須項目の欠落を防止

### 6.2 トランザクション

PostgreSQLのACID特性により、複数テーブルへの操作の原子性を保証する。

**使用ケース**:

**1. テナント削除時の関連データ削除**
```sql
BEGIN;
  -- 契約情報を削除（外部キー制約でCASCADE削除も可能）
  DELETE FROM tenant_service_subscription WHERE tenant_id = 'tenant-001';
  
  -- テナント情報を削除
  DELETE FROM tenant WHERE tenant_id = 'tenant-001';
COMMIT;
```

**2. サービス契約登録**
```sql
BEGIN;
  -- テナントの存在確認
  SELECT tenant_id FROM tenant WHERE tenant_id = 'tenant-001' FOR UPDATE;
  
  -- サービスの存在確認
  SELECT service_id FROM service WHERE service_id = 'service-001' FOR UPDATE;
  
  -- 契約登録
  INSERT INTO tenant_service_subscription (tenant_id, service_id, access_level)
  VALUES ('tenant-001', 'service-001', 'PREMIUM');
COMMIT;
```

### 6.3 データバリデーション

**アプリケーションレベル**:
- 入力値の型チェック
- 文字列長の検証
- 日付の妥当性チェック

**データベースレベル**:
- CHECK制約による値の制限
- NOT NULL制約による必須チェック
- UNIQUE制約による重複防止

## 7. パフォーマンス設計

### 7.1 アクセスパターン

**主要なアクセスパターン**:

| パターン | 頻度 | SQL例 |
|---------|------|-------|
| テナント情報取得 | 高 | `SELECT * FROM tenant WHERE tenant_id = ?` |
| サービス一覧取得 | 高 | `SELECT * FROM service WHERE status = 'active'` |
| 契約サービス取得 | 高 | `SELECT * FROM tenant_service_subscription WHERE tenant_id = ? AND status = 'active'` |
| サービス別契約一覧 | 低 | `SELECT * FROM tenant_service_subscription WHERE service_id = ?` |

### 7.2 パフォーマンス最適化

**1. インデックスの活用**

適切なインデックスにより、検索性能を向上。

**2. 接続プーリング**

Lambda関数からの接続を効率化するため、接続プーリングを使用。

**3. キャッシング戦略**

| データ | キャッシュ | TTL | 理由 |
|--------|-----------|-----|------|
| サービス一覧 | ✓ | 1時間 | 更新頻度が低い |
| テナント情報 | ✓ | 5分 | 認証時に頻繁にアクセス |
| 契約情報 | - | - | リアルタイム性が重要 |

**4. クエリ最適化**

```sql
-- 悪い例（N+1問題）
SELECT * FROM tenant_service_subscription WHERE tenant_id = 'tenant-001';
-- 各サービスIDに対して個別にSELECT

-- 良い例（JOIN使用）
SELECT tss.*, s.service_name, s.service_url
FROM tenant_service_subscription tss
JOIN service s ON tss.service_id = s.service_id
WHERE tss.tenant_id = 'tenant-001' AND tss.status = 'active';
```

## 付録

### A. PostgreSQL設計のベストプラクティス

1. **主キーの選択**
   - UUID型を使用（分散環境でも一意性を保証）
   - `gen_random_uuid()`で自動生成

2. **インデックスの設計**
   - WHERE句で頻繁に使用するカラムにインデックス
   - 複合インデックスは選択性の高い順に

3. **データ型の選択**
   - 日時: TIMESTAMP型
   - ID: UUID型
   - ステータス: VARCHAR型（CHECK制約で制限）
   - JSON: JSONB型（検索・インデックス可能）

4. **制約の活用**
   - 外部キー制約で参照整合性を保証
   - CHECK制約で値の範囲を制限
   - UNIQUE制約で重複を防止

### B. 初期データ投入スクリプト

```sql
-- サンプルテナント
INSERT INTO tenant (tenant_name, company_name, status, contract_start_date, auth_method)
VALUES
```
